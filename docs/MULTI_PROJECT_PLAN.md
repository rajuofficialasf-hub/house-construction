## ১. সারসংক্ষেপ

এখনকার সাইটটি শুধু "ঘর নির্মাণ প্রকল্প"-এর জন্য বানানো, যার ভেতরে দুটি অংশ: সেমিপাকা আর টিন। এই পরিকল্পনা মেনে সাইটটি একটি **বহু-প্রকল্প প্ল্যাটফর্ম** হবে। এডমিন প্যানেল (`/admin`) থেকে কোড ছাড়াই যা করা যাবে:
- বাংলা ও ইংরেজি নামসহ নতুন প্রকল্প খোলা: আলাদা প্রকল্প, কোনো গ্রুপের ভেতরে উপ-প্রকল্প, অথবা নতুন গ্রুপ।
- প্রতিটি প্রকল্পের ফিল্ড ঠিক করা, যেমন উপকরণের ক্যাটাগরি বা টাকা।
- ক্যাটাগরির জন্য আলাদা তালিকা বানাতে হবে না। শীটের "ক্যাটাগরি" কলামে যা লেখা থাকবে (যেমন গরু, ছাগল, মুদি দোকান), সেটাই ক্যাটাগরি; সিস্টেম নিজে থেকে গুনে "মোট ক্যাটাগরি" দেখাবে।
- ছবির ধরন বেছে নেওয়া: আগে-পরে, নাকি শুধু পরে।
- ঠিকানা কোন স্তর পর্যন্ত যাবে, তা ঠিক করা: উপজেলা পর্যন্ত, নাকি ইউনিয়ন পর্যন্ত।
- স্ট্যাট কার্ড বাছাই করা: মোট উপকারভোগী, মোট টাকা, মোট ক্যাটাগরি ইত্যাদি।

প্রতিটি প্রকল্প নিজের URL-এ (`/housing`, `/self-reliance`, `/skill-based-entrepreneur`) শুধু নিজের ডাটা দেখাবে: স্ট্যাট, ম্যাপ, ফিল্টার, তালিকা আর বিস্তারিত। হোম পেইজে থাকবে সব প্রকল্পের ডায়নামিক কার্ড।

যা অক্ষত থাকবে:
- লাইভ ১০টি সেমিপাকা রেকর্ড, ৪টি ছবি, সিরিয়াল নম্বর আর পুরনো লিংক।
- নিরাপত্তার সব নিয়ম।

লাইভ ডাটায় কোনো পরীক্ষামূলক সংরক্ষণ হবে না। সব পরীক্ষা হবে হয় উল্টে-দেওয়া (ROLLBACK) SQL-এর ভেতরে, নয়তো একটি আলাদা "পরীক্ষা প্রকল্প"-এ।

কাজ হবে **১৬টি ধাপে (M-ধাপ ১–১৬)**। M-ধাপ ৫ দুটি বার্তায় ভাগ করা: ৫ক ও ৫খ। প্রতিটি ধাপ শেষে সাইট চালু অবস্থায় থাকবে।

### ১.১ কীভাবে এই পরিকল্পনা ব্যবহার করবেন

1. **আপনার যা পড়লেই চলবে:** §১, §২, §৩, §৪, §৭, আর §৮-এ প্রতিটি ধাপের "আমাকে যা করতে হবে"। §৫ ও §৬ কারিগরি অংশ, AI-এর জন্য লেখা। এগুলো না পড়লেও চলবে।
2. §৭-এর প্রশ্নগুলো পড়ুন। উত্তর দিন, অথবা লিখুন "সব ডিফল্ট ঠিক আছে"। **উত্তর না দিলে AI সুপারিশকৃত ডিফল্ট ধরে এগোবে।** যে ধাপে সেটা প্রয়োগ হবে, তার শুরুতে জানাবে এবং §১২-এর সিদ্ধান্ত লগে লিখে রাখবে।
3. প্রতি বার্তায় একটি ধাপ চাইবেন, যেমন: `M-ধাপ ৩ শুরু করো`।
4. প্রতিটি ধাপের শুরুতে AI দুটি ফাইল পড়বে: এই পরিকল্পনা আর `docs/HOUSING_PROGRESS.md`। M-ধাপ ১-এ পরিকল্পনাটি পড়বে ডেস্কটপের ফাইল থেকে, পরের ধাপগুলোতে `docs/MULTI_PROJECT_PLAN.md` থেকে।
5. প্রতিটি ধাপের শেষে পাবেন (১) কোন ফাইল বদলেছে, (২) "আমাকে যা করতে হবে", (৩) কীভাবে পরীক্ষা করবেন।
6. git কমিট বা পুশ হবে শুধু আপনার অনুমতিতে (প্রশ্ন ১৮)।

### ১.৩ Supabase SQL Editor-এ ফাইল চালানোর নিয়ম

প্রতিবার SQL চালানোর সময় হুবহু এভাবে করবেন:
1. ব্রাউজারে supabase.com খুলুন। প্রকল্প `bmyjwsxmigsdemtpllgd` বেছে নিন, তারপর বাম মেনু থেকে **SQL Editor**।
2. **New query** চাপুন, যাতে একটি খালি পাতা আসে।
3. VS Code বা Notepad-এ নির্দিষ্ট ফাইলটি খুলুন (যেমন `supabase/sql/10_projects.sql`)। তারপর **Ctrl+A** চেপে সব বাছাই করুন, **Ctrl+C** চেপে কপি করুন।
4. SQL Editor-এ **Ctrl+V** দিন। **পুরো ফাইল একবারে** পেস্ট করবেন, কোনো অংশ বাদ দেবেন না বা আলাদা করে চালাবেন না।
5. **Run** চাপুন (অথবা Ctrl+Enter)। "Potential issue detected" ধরনের সতর্কতা এলে, শুধু এই পরিকল্পনার ফাইলের ক্ষেত্রে **Run this query** চাপুন।
6. **সফল হলে:** নিচে একটি ফলাফলের টেবিল আসবে, যার প্রতিটি সারিতে ✅ বা ❌। পুরো টেবিলটি কপি করে (অথবা স্ক্রিনশট নিয়ে) AI-কে পাঠান।
7. **লাল ত্রুটি এলে:**
   - আবার Run করবেন না।
   - ফাইলের কোনো অংশ আলাদা করে চালাবেন না।
   - পুরো লাল বার্তাটি কপি করে AI-কে পাঠান।
   - প্রতিটি ফাইল "সব অথবা কিছুই না" নিয়মে লেখা (`begin … commit`)। তাই ত্রুটি হলে ডাটাবেসে **কিছুই বদলায়নি**।
8. প্রতিটি ফাইল শেষে **একটিমাত্র ফলাফল-টেবিল** দেখাবে, কারণ SQL Editor শুধু শেষ ফলাফলটি দেখায়।

তালিকা পেইজে নতুন query প্যারামিটার:

- `f_<fieldKey>=`: ক্যাটাগরি ফিল্টার, যেমন `?f_category=গরু` (URL-এ এনকোড হয়ে যায়)

### ৪.২ এডমিন (সব পেইজ lazy-load হবে)

| URL | কাজ |
|---|---|
| `/admin/login` | লগইন |
| `/admin` | ড্যাশবোর্ড: খসড়াসহ প্রতিটি প্রকল্পের একটি কার্ড, যাতে থাকবে রেকর্ড সংখ্যা, মোট টাকা, কতটিতে ছবি বাকি, আর দ্রুত লিংক |

- slug বদলালেও বুকমার্ক ভাঙবে না।
- `import` বা `photos`-এর মতো স্থির শব্দের সাথে কোনো সংঘর্ষ হবে না।

### ৪.৪ slug-এর নিয়ম

ডাটাবেস (CHECK ও ট্রিগার) আর ফর্ম, দুই জায়গাতেই এই নিয়মগুলো যাচাই হবে:
- ফরম্যাট `^[a-z0-9]+(-[a-z0-9]+)*$`, সর্বোচ্চ ৬০ অক্ষর। ডট রাখা যায় না, তাই `favicon.svg` বা `index.html`-এর মতো ফাইলের সাথে সংঘর্ষ সম্ভব নয়।
- শুধু সংখ্যা দিয়ে slug হবে না, কারণ তাতে `:serial`-এর সাথে গোলমাল হয়।
- **সারা সাইটে অনন্য** হতে হবে, শুধু একই গ্রুপের ভেতরে অনন্য হলে চলবে না।
- সংরক্ষিত শব্দ, যেগুলো slug হিসেবে নেওয়া যাবে না: `admin, api, auth, login, logout, assets, geo, static, src, public, node-modules, favicon, icons, dev, projects, records, search, about, contact, donate, news, en, bn, new, edit, import, photos, activity, settings, users, preview, index`। এর মধ্যে `src` ও `public` সংরক্ষিত, কারণ LAN ডেমোর dev সার্ভার `/src/*` পরিবেশন করে।
- **প্রকাশিত প্রকল্পের slug বদলানো যাবে না।** বদলাতে হলে আগে অপ্রকাশিত করতে হবে, আর তখন সতর্কবার্তা আসবে: "শেয়ার করা লিংক ভাঙবে"। এই নিয়মের কারণে আলাদা রিডাইরেক্ট টেবিলের দরকার পড়ে না।

| `is_group` | boolean | গ্রুপে রেকর্ড, ফিল্ড, ছবি বা ফাইল-প্রিফিক্স থাকে না |
| `slug` | text, **unique**, §৪.৪-এর নিয়ম | URL অংশ |
| `name_bn`, `name_en` | NOT NULL, খালি নয়, ≤১২০ অক্ষর | **দুটোই আবশ্যক** |
| `summary_bn`, `summary_en` | default '', ≤৩০০ | কার্ডের ছোট বর্ণনা |
| `description_bn`, `description_en` | default '', ≤২০০০, শুধু সাধারণ লেখা | পেইজের পরিচিতি |
| `unit_bn`, `unit_en` | default 'উপকারভোগী' / 'beneficiaries' | ম্যাপ ও স্ট্যাটের একক শব্দ (ঘরে: ঘর / houses) |
| `photo_mode` | `before_after` \| `after_only` \| `none` | |
| `prev_label_bn/en`, `current_label_bn/en` | text | যেমন "পূর্বের ঘর" বা "উপকরণসহ ছবি" |
| `geo_depth` | `upazila` \| `union` | |
| `core_fields` | jsonb object | সিস্টেম ফিল্ডের সেটিং (নিচে উদাহরণ) |
| `stat_cards` | jsonb array, সর্বোচ্চ ৮টি কার্ড, `home:true` সর্বোচ্চ ৩টি | |
| `display` | jsonb | `{ "show_map": true, "geo_columns": "split"\|"merged", "breakdown_field": "category" }` |
| `file_prefix` | text unique, `^[a-z][a-z0-9]{0,15}$` (গ্রুপে null) | ছবির ফাইলনামের শুরু: `semi`, `tin`, `sr`, `skill` |
| `icon`, `accent` | কোডে রাখা নির্দিষ্ট তালিকার key | আইকন আর রং (কাঁচা CSS কখনো নয়) |
| `cover_path` | text null | কভার ছবির স্টোরেজ পাথ (URL নয়) |
| `sort_order`, `is_published` (default false), `show_on_home` (default true) | | |
| `created_at`, `updated_at` | | `updated_at` দিয়ে দুই এডমিনের একসাথে এডিট ধরা হয় |

**সবসময় চালু ও আবশ্যক সিস্টেম ফিল্ড:** `name`, `division`, `district`, `upazila` আর **`year`**। এগুলোর শুধু লেবেল বদলানো যাবে। প্রশ্ন ৩-এর উত্তর "না" হলে নিয়ম বদলাবে: SQL ১০-এ `year` nullable হবে, আর যাচাই ট্রিগার প্রকল্প অনুযায়ী `core_fields.year.required` দেখে চলবে। ততদিন প্যানেলে `year`-এর "ঐচ্ছিক/বন্ধ" অপশন দেখাবে না।

`core_fields` উদাহরণ:
```json
{ "year": { "label_bn": "অনুদানের সাল", "label_en": "Grant year" },
  "father_or_husband_name": { "enabled": true, "required": false },
  "address": { "enabled": true, "required": false },
  "union_name": { "required": true } }
```

`stat_cards` উদাহরণ। এখানে শুধু উপস্থাপনার কনফিগ থাকে; সংখ্যা আসে `project_stats` থেকে। (M-ধাপ ২-এ যোগ: ঐচ্ছিক `home_label_bn`/`home_label_en` — হোম কার্ডে আলাদা লেবেল, যেমন তালিকায় "মোট উপকারভোগী" কিন্তু হোমে "মোট ঘর নির্মাণ"; এখনকার দুই পেইজের লেবেল হুবহু রাখতে।)
```json
[ { "id": "total",    "kind": "count",                         "label_bn": "মোট উপকারভোগী", "label_en": "Total beneficiaries", "icon": "users", "home": true },
  { "id": "money",    "kind": "sum",      "field": "amount",   "label_bn": "মোট টাকা",       "label_en": "Total amount",        "icon": "coins", "home": true, "format": "money" },
  { "id": "cats",     "kind": "distinct", "field": "category", "label_bn": "মোট ক্যাটাগরি",  "label_en": "Total categories",    "icon": "tags",  "home": true },
  { "id": "districts","kind": "geo",      "level": "district", "label_bn": "জেলা কভার",      "label_en": "Districts covered",   "icon": "map" } ]
```
`kind` চার রকম:
- `count`: মোট রেকর্ড
- `geo`: বিভাগ, জেলা, উপজেলা বা ইউনিয়ন কভার
- `sum`: টাকা বা সংখ্যার যোগফল
- `distinct`: ক্যাটাগরির ভিন্ন মানের সংখ্যা

গ্রুপের ডিফল্ট কার্ড হলো `count` আর `geo`, যা উপ-প্রকল্পগুলোর যোগফল দেখায়।

### ৫.৩ নতুন টেবিল `project_fields` (এডমিনের বানানো ফিল্ড)

| কলাম | নিয়ম |

| `id` | uuid PK |
| `project_key` | → `projects(key)` ON DELETE RESTRICT। শুধু একক বা উপ-প্রকল্পের ফিল্ড হয়, গ্রুপের নয়। |
| `key` | `^[a-z][a-z0-9_]{0,39}$`, প্রকল্পের ভেতরে অনন্য। এগুলো হতে পারবে না: সিস্টেম কলামের নাম (`id, project_type, serial_no, year, name, father_or_husband_name, division, district, upazila, union_name, address, extra, created_at, updated_at, photo_updated_at`), `prev_*`/`current_*`, অথবা `q, page, sort, f`। **ডাটা আসার পর অপরিবর্তনীয়।** |
| key তৈরির নিয়ম | ইংরেজি লেবেল থেকে অটো তৈরি হয়। ইংরেজি লেবেল খালি থাকলে বাংলা থেকে লিপ্যন্তর (transliteration) করে, তাও না হলে `field_<n>`। ডাটা আসার আগ পর্যন্ত হাতে বদলানো যায়। |

| `type` | §৫.৪-এর তালিকা থেকে। ডাটা আসার পর অপরিবর্তনীয়। |
| `options` | jsonb, default `[]`। এখন **ব্যবহার হবে না** (ভবিষ্যতের `select` ধরনের জন্য জায়গা রাখা, §১০) |

প্রতি প্রকল্পে সর্বোচ্চ ৪০টি ফিল্ড।

**ক্যাটাগরির মান কোথা থেকে আসে:** কোনো অপশন-তালিকা নেই। রেকর্ডের `extra.category`-তে শীট বা ফর্মে লেখা মানটিই (স্বাভাবিক করে) জমা হয়, যেমন `"গরু"`। ফিল্টারের ড্রপডাউন আর বিতরণ চার্ট তৈরি হয় ডাটায় আসলে থাকা মানগুলো থেকে (`project_stats`-এর `by_value`)। ইংরেজি মোডে মানটি যেমন লেখা তেমনই দেখায়, নামের মতো।

### ৫.৪ ফিল্ডের ধরন

| `type` | প্যানেলে নাম | কীভাবে জমা হয় | যাচাই (সার্ভার ও ফর্মে একই নিয়ম) | স্ট্যাট / ফিল্টার |
|---|---|---|---|---|
| `text` | লেখা | JSON string, NFC | ≤ `max_length` (ডিফল্ট ৫০০) | ঐচ্ছিকভাবে সার্চে |
| `long_text` | বড় লেখা | string | ≤২০০০ | — |
| `number` | সংখ্যা | JSON number | min/max, ≤২ দশমিক | যোগফল |
| `money` | টাকা | JSON number, **পূর্ণসংখ্যা** | ≥০ এবং ≤১০০০ কোটি (1e11)। ফর্ম ও ইম্পোর্টে বাংলা অঙ্ক, কমা, `৳`, `টাকা`, `Tk` আর `/-` গ্রহণ করে। | যোগফল ("মোট টাকা") |
| `category` | ক্যাটাগরি (শীটের লেখা থেকে) | JSON string: NFC, `btrim`, একাধিক ফাঁকা → একটি | খালি নয় (আবশ্যক হলে), ≤১০০ অক্ষর | ভিন্ন মানের সংখ্যা ("মোট ক্যাটাগরি"), ফিল্টার ড্রপডাউন (ডাটার মান থেকে), বিতরণ চার্ট |
| `date` | তারিখ | `YYYY-MM-DD` | বৈধ তারিখ | — |

### ৫.৫ রেকর্ড টেবিল `housing_beneficiaries`-এ পরিবর্তন (শুধু যোগ, কিছু মোছা হবে না)

1. **ক্রম মেনে:** প্রথমে `projects`-এ ৩টি seed সারি। তারপর `project_type`-এ `FOREIGN KEY → projects(key) ON UPDATE RESTRICT ON DELETE RESTRICT`। তারপর পুরনো `housing_beneficiaries_project_type_check` বাদ। এতে কোনো মুহূর্তেই টেবিল constraint ছাড়া থাকে না।
2. `union_name text NOT NULL DEFAULT ''` যোগ। নাম `union` রাখা যাবে না, কারণ এটা SQL-এর সংরক্ষিত শব্দ।
3. `extra jsonb NOT NULL DEFAULT '{}'` যোগ, সাথে CHECK `jsonb_typeof(extra)='object'`। আকার ১৬ KB-এর কম।
4. ইনডেক্স:
   - `GIN (extra)`
   - `(project_type, district, upazila)`
   - `(project_type, union_name) WHERE union_name <> ''`
   - `(project_type, created_at desc)`
5. পুরনো সারিগুলো নতুন কলামে শুধু ডিফল্ট মান পাবে। আর কোনো মান বদলাবে না, `updated_at`-ও না, কারণ কলাম যোগ করলে ট্রিগার চলে না।

### ৫.৬ গোপন ফিল্ড: `beneficiary_private`

কলাম: `record_id uuid PK → housing_beneficiaries(id) ON DELETE CASCADE, data jsonb NOT NULL DEFAULT '{}', updated_at`
- RLS: পড়া ও লেখা দুটোই শুধু `is_housing_admin()`।
- ট্রিগার নিশ্চিত করবে যে:
  - এখানে শুধু `visibility='admin'` ফিল্ডের key থাকে।
  - পাবলিক `extra`-তে কোনো এডমিন-ফিল্ডের key **ঢুকতে পারে না**।
- ফলে স্ক্রিপ্ট বা UI-তে বাগ থাকলেও মোবাইল নম্বর বা NID ফাঁস হয় না।
- একটিভিটি লগে গোপন ফিল্ডের শুধু নাম লেখা হয়, মান নয়।

### ৫.৭ সার্ভারে যাচাই: `housing_validate_record()`

ট্রিগারের নাম `housing_beneficiaries_validate`: BEFORE INSERT/UPDATE, SECURITY DEFINER (যাতে RLS-এর আড়ালে থাকা `projects`/`project_fields` পড়তে পারে), স্থির `search_path = public`। নামের বর্ণানুক্রম অনুযায়ী এটি বিদ্যমান assign, protect ও updated_at ট্রিগারের পরে চলে।

ট্রিগার যা যা করে:
1. প্রকল্পটি আছে কি না, আর গ্রুপ নয় তো, যাচাই করে।
2. সিস্টেম টেক্সটে (নাম, পিতা, বিভাগ, জেলা, উপজেলা, ইউনিয়ন, ঠিকানা) `normalize(btrim(x), NFC)` প্রয়োগ করে। এতদিন NFC শুধু ক্লায়েন্টে হতো; এখন সার্ভারেও হবে।
3. `core_fields` অনুযায়ী আবশ্যক সিস্টেম ফিল্ড যাচাই করে।
4. `after_only` বা `none` প্রকল্পে `prev_*` ছবি সেট করতে দেয় না।
5. `extra` যাচাই করে:
   - `null` বা `''` মানের key সরিয়ে দেয়।
   - অচেনা key আর এডমিন-ফিল্ডের key বাতিল করে।
   - ধরন মেলায় (§৫.৪), আর টেক্সট NFC করে।
   - UPDATE-এ শুধু **নতুন বা বদলানো** key যাচাই করে, যাতে পরে সংজ্ঞা বদলালেও পুরনো রেকর্ড আটকে না যায়।
6. আবশ্যক কাস্টম ফিল্ড:
   - INSERT-এ অবশ্যই থাকতে হবে।
   - UPDATE-এ শুধু একটি নিয়ম: আগে মান ছিল, এখন খালি করা যাবে না।
7. আর্কাইভ করা ফিল্ডের পুরনো মান থেকে যায়, কিন্তু নতুন মান দেওয়া যায় না।
8. ভুল হলে `errcode 23514` দেয়, বাংলা বার্তায় ফিল্ডের লেবেলসহ, আর `DETAIL` = `extra.<key>`। বিদ্যমান `errors.ts` এটাকে আগে থেকেই `VALIDATION_ERROR`-এ রূপান্তর করে।

### ৫.৮ ডাটা হারানো ঠেকানোর গার্ড (ডাটাবেস নিজেই আটকায়)

| কাজ | কখন অনুমোদিত | না হলে |
|---|---|---|
| প্রকল্পের `key` বদল | কখনো নয় | ত্রুটি |

| `slug` বা `parent_key` বদল | শুধু অপ্রকাশিত অবস্থায় | ত্রুটি |
| `is_group` বদল | কোনো রেকর্ড বা উপ-প্রকল্প না থাকলে | ত্রুটি |
| ছবি মোড আগে-পরে থেকে শুধু-পরে বা ছবি-নেই | কোনো রেকর্ডে আগের ছবি না থাকলে | ত্রুটি, সাথে কতটি রেকর্ডে আছে তার সংখ্যা |
| অপ্রকাশ (প্রকাশ বন্ধ) | অনুমোদিত, কিন্তু রেকর্ড বা প্রকাশিত উপ-প্রকল্প থাকলে UI-তে নিশ্চিতকরণ চাওয়া হয় (M-ধাপ ৭) আর লগে `project_unpublish` লেখা হয় | — |
| ফিল্ডের `key`, `type` বা `visibility` বদল | কোনো রেকর্ডে মান না থাকলে | ত্রুটি |
| ফিল্ড মোছা | মান না থাকলে | ত্রুটি, সাথে পরামর্শ: আর্কাইভ |
| ক্যাটাগরির একটি মান সব রেকর্ডে বদলানো (বানান একীকরণ) | শুধু এডমিন, `project_field_rename_value` দিয়ে; প্রতিটি বদল লগে যায় | — |
| রেকর্ডের প্রকল্প বদল | কখনো নয় (আগে থেকেই `02_serial.sql`-এ আছে) | ত্রুটি |
| দুই এডমিন একসাথে এডিট | `updated_at` মিললে | `CONFLICT`: "অন্য কেউ এর মধ্যে বদলেছেন, রিফ্রেশ করুন" |
| নতুন প্রকল্প তৈরি | — | AFTER INSERT ট্রিগার নিজে থেকেই `housing_serial_counters`-এ `(key, 0) ON CONFLICT DO NOTHING` বসায়। বিদ্যমান কাউন্টারে কখনো হাত দেয় না। |

**SECURITY DEFINER নিয়ম:** `housing_serial_counters`-এ RLS চালু আছে কিন্তু কোনো পলিসি নেই। তাই সাধারণ এডমিন সেশন থেকে এটা পড়া বা লেখা যায় না। ফলে যে ফাংশনগুলো এই টেবিল পড়ে বা লেখে, সবগুলোই `SECURITY DEFINER` হবে, সাথে `set search_path = public`:
- কাউন্টার-তৈরির ট্রিগার
- মোছার গার্ড
- `project_create`
- `dev/remove_demo_project.sql`-এর ফাংশন

এটা না করলে কাউন্টার ইনসার্ট ব্যর্থ হতো। তার চেয়েও খারাপ, মোছার গার্ড কোনো সারি না পেয়ে সেটাকে "০" ধরে নিত, আর ব্যবহৃত প্রকল্প মুছে ফেলা যেত। তখন key আবার তৈরি করলে সিরিয়াল পুনর্ব্যবহার হয়ে যেত। selftest-এ এগুলো আসল এডমিন সেশনের মতো করে পরীক্ষা হবে (§৫.১৮)।

### ৫.৯ RLS ও খসড়া

হেল্পার `public_project_keys()` (STABLE, SECURITY DEFINER, anon ও auth দুজনকেই grant): যে প্রকল্পগুলো প্রকাশিত, এবং যাদের গ্রুপও প্রকাশিত, শুধু সেগুলোর key ফেরত দেয়।

| টেবিল | পড়া (SELECT) | লেখা |
|---|---|---|
| `projects` | `key = any((select public_project_keys())) or (select is_housing_admin())` | শুধু এডমিন |
| `project_fields` | (প্রকল্প পাবলিক **এবং** `visibility='public'`) অথবা এডমিন | শুধু এডমিন |
| `housing_beneficiaries` | `using(true)`-এর **বদলে** `project_type = any((select public_project_keys())) or (select is_housing_admin())` | শুধু এডমিন (অপরিবর্তিত) |
| `beneficiary_private` | শুধু এডমিন | শুধু এডমিন |

ব্যাখ্যা:
- ফাংশনগুলো `(select …)`-এর ভেতরে মোড়ানো, তাই প্রতি সারিতে নয়, প্রতি কোয়েরিতে একবার চলে।
- প্রতিটি নতুন টেবিলে RLS চালু হবে টেবিলটি যে SQL ফাইলে তৈরি হয়, সেই ফাইলেই।
- `housing_next_serial` এখন anon-ও চালাতে পারে, আর এটা SECURITY DEFINER। ফলে এটা খসড়া প্রকল্পের রেকর্ড সংখ্যা ফাঁস করে দিতে পারে। SQL ১১-এ নিয়ম যোগ হবে: প্রকল্পটি পাবলিক নয় এবং কলকারী এডমিন নয়, তাহলে `null` ফেরত। signature অপরিবর্তিত থাকবে।
- **খসড়ার ছবি লুকানো থাকে না।** bucket `housing-photos` পাবলিক, আর পাথ সম্পূর্ণ অনুমানযোগ্য (`housing/{key}/0001/current.webp`)। তাই খসড়া প্রকল্পের ছবি যে কেউ সহজেই খুঁজে পেতে পারে। নিয়ম:
  - খসড়ায় কখনো আসল উপকারভোগীর ছবি নয়, শুধু পরীক্ষার ছবি।
  - আসল ছবি আপলোড হবে প্রকাশের **পরে** (M-ধাপ ১৬-এর ক্রম, প্রশ্ন ১৯)।
- **ভূমিকা (প্রশ্ন ১৬, ২০২৬-১০-০৫):** একজন মূল এডমিন (`main_admin`) সব পারেন, মোছাসহ; সাধারণ এডমিন (`admin`) যোগ ও এডিট পারেন, কোনো কিছু মুছতে পারেন না (RLS: delete পলিসি `is_housing_main_admin()`; ছবি সরানো যাচাই-ট্রিগারে; Storage-এর delete পলিসি)। UI-তে মোছার বোতাম সাধারণ এডমিনের কাছে লুকানো থাকবে (M-ধাপ ৭, ১০, ১২)। প্রকল্পভিত্তিক এডিটর পরে যোগ করা যাবে (§১০)।

### ৫.১০ RPC (SQL ফাংশন)

| RPC | ধরন | কাজ |

| `projects_overview(p_include_drafts default false)` | INVOKER, anon | হোম পেইজ আর এডমিন ড্যাশবোর্ডের জন্য **একটি কলেই** সব: প্রতি প্রকল্পের হালকা স্ট্যাট, সর্বশেষ রেকর্ডের থাম্ব (কভার না থাকলে), আর `global {projects, total, districts}`। খসড়া আসে শুধু এডমিন `true` পাঠালে, সাথে `without_photo` গণনা। |
| `project_create(p_project jsonb, p_fields jsonb)` | DEFINER, এডমিন যাচাইসহ | প্রকল্প আর তার ফিল্ড **একসাথে** তৈরি করে। একটি ফিল্ডও ভুল হলে কিছুই তৈরি হয় না। |
| `projects_reorder(p_keys)`, `project_fields_reorder(p_project, p_ids)` | DEFINER, এডমিন | ক্রম বদল |

| `housing_bulk_update_by_serial` **v2** | INVOKER, signature অপরিবর্তিত | নিচে বিস্তারিত |

`housing_bulk_update_by_serial` v2-এর নিয়ম:
- প্রকল্প যাচাই হয় হার্ডকোড তালিকার বদলে রেজিস্ট্রি থেকে।
- key না থাকা, `null` বা `''` মানে **অপরিবর্তিত**। এতে এখনকার বাগ ঠিক হয়: আজ update মোডে পিতার নাম আর ঠিকানা মুছে যায়।
- কোনো মান **মুছতে** চাইলে সারিতে স্পষ্ট তালিকা দিতে হয়: `"_clear": ["address", "extra.item_name"]`। আবশ্যক ফিল্ড মোছা যায় না।
- `union_name` যোগ হয়েছে।
- কাস্টম মান মার্জ হয়: `extra = b.extra || patch`। গোপন অংশ যায় `beneficiary_private`-এ।

`project_stats`-এর উত্তরের শেপ। এটি এখনকার শেপের সাথে শুধু যোগ, তাই পুরনো কোড ভাঙে না।
```json
{ "total": 120, "by_year": {"2025": 80}, "by_division": {}, "by_district": {}, "by_upazila": {},
  "by_location": {"চট্টগ্রাম|মীরসরাই": 12},
  "by_union":    {"চট্টগ্রাম|মীরসরাই|জোরারগঞ্জ": 4},
  "distinct": {"divisions": 3, "districts": 9, "upazilas": 20, "unions": 41},
  "fields": {
    "amount":   {"type": "money",  "sum": 2450000, "count": 118},
    "category": {"type": "category", "distinct": 4, "by_value": {"গরু": {"n": 45, "sums": {"amount": 1575000}}}} },
  "by_project": {"semi_pucca": 10, "tin": 0} }
```
গণনার নিয়ম:
- `fields`-এর হিসাব হয় শুধু সক্রিয় ও **পাবলিক** ফিল্ডের ওপর লুপ চালিয়ে।
- ফিল্ডের key যায় প্যারামিটার হিসেবে (`extra->f.key`)। dynamic SQL নেই, তাই injection-এর সুযোগ নেই।
- যোগফলে ধরা হয় শুধু `jsonb_typeof = 'number'` মানগুলো, তাই খারাপ ডাটা থাকলেও কোয়েরি ভাঙে না।
- `category`-র `distinct` আর `by_value` হিসাব হয় জমা-থাকা (আগেই স্বাভাবিক করা) লেখার ওপর; খালি মান গোনা হয় না।
- বছরের তালিকা আসে `by_year`-এর key থেকে।

### ৫.১১ ছবি ও স্টোরেজ

- দুটি স্থির স্লট `prev` আর `current`; `PhotoKind` বদলাবে না।
  - `before_after`: দুটি স্লটই ব্যবহার হয়।
  - `after_only`: শুধু `current`। ডাটাবেস ট্রিগার আর adapter দুই জায়গাতেই `prev` বাতিল হয়।
  - `none`: কোনো ছবি নেই।
- পাথের নিয়ম সব প্রকল্পে একই, অপরিবর্তিত: `housing/{project_key}/{0001}/{prev|current}[_thumb].webp`।
  - উদাহরণ: `housing/self_reliance/0001/current.webp`।
  - এখানে "housing" শুধু ভেতরের একটি নামস্থান; দর্শক কখনো দেখেন না।
  - **৪টি লাইভ ছবি, তাদের URL আর `photo_updated_at`-ভিত্তিক `?v=` ক্যাশ-বাস্টিং হুবহু থাকবে।**
- কভার ছবি থাকবে `housing/_projects/{key}/cover.webp`-এ। key `_` দিয়ে শুরু হতে পারে না, তাই এখানে সংঘর্ষ অসম্ভব।
- ছবির ফাইলনাম:
  - আগে-পরে প্রকল্প: `semi_0001_prev.jpg`, `tin_12_after.png` (আগের মতো)।
  - শুধু-পরে প্রকল্প: `sr_0012.jpg`। ড্রপডাউনে প্রকল্প বাছাই করা থাকলে শুধু `0012.jpg`। দুটোই `current` হিসেবে ধরা হয়।

### ৫.১২ ভূগোল ও ইউনিয়ন

- বিভাগ, জেলা ও উপজেলা আগের মতো `bdGeo.ts` থেকে আসবে (৮টি বিভাগ, ৬৪টি জেলা, ৪৯৪টি উপজেলা)। ম্যাপ **উপজেলা-স্তরেই** থাকবে।
- **ইউনিয়নের উৎস:** nuhil/bangladesh-geocode-এর `unions/unions.json` (MIT লাইসেন্স)। এতে ৪,৫৪০টি ইউনিয়ন আছে, যা ৪৯৪টি উপজেলার মধ্যে ৪৮৯টি কভার করে। bdGeo-র সাথে join মিলিয়ে দেখা হয়েছে: ৪৯৪/৪৯৪।
- `scripts/build-unions.mjs` যা করবে:
  - সব নাম NFC করবে (৯০৮টি NFC নয়) আর trim করবে (৪টির শুরুতে ফাঁকা আছে)।
  - ৩টি ডুপ্লিকেট জোড়া বাদ দেবে।
  - ২টি ভাঙা ইংরেজি নাম ঠিক করবে।
  - `unionOverrides.json` মিশিয়ে দেবে।
- আউটপুট `src/features/geo/data/bd-unions.json`, আকারে প্রায় ৫৩ KB gzip। এটি **lazy `import()`** দিয়ে লোড হবে, তাই মূল বান্ডেলে কখনো ঢুকবে না। Vite-এর hash থাকায় আপডেট হলে ক্যাশ নিজে থেকেই বদলাবে।
- যে ৫টি উপজেলায় কোনো ইউনিয়ন নেই (গুইমারা, নলডাঙ্গা, ঈদগাঁও, মধ্যনগর, ডাসার), সেগুলোর তালিকা **অনুমান করে বানানো হবে না।**
- ইনপুট হবে কম্বোবক্স:
  - নির্বাচিত উপজেলার ইউনিয়নগুলো সাজেশন হিসেবে আসবে।
  - নিজে লেখাও চলবে। তালিকায় না থাকলে হলুদ সতর্কবার্তা দেখাবে, কিন্তু সংরক্ষণ আটকাবে না।
  - একটি "পৌরসভা" চিপ থাকবে, যেমন "মীরসরাই পৌরসভা"।
- fuzzy মিলের সময় "পৌরসভা" আর "ওয়ার্ড" শব্দ বাদ দেওয়া হবে না।
- ইউনিয়নের ইংরেজি নাম আসবে `gnUnion(district, upazila, union)` থেকে। ৩২৭টি ইউনিয়নের নাম দেশে একাধিকবার আছে, তাই সবসময় পুরো পথ ধরে খোঁজা হবে।
- ইউনিয়ন ফিল্টারের অপশন আসবে ডাটাবেসে থাকা আসল মান (`stats.by_union`) থেকে।

### ৫.১৩ ডাটাবেসের লেখার ভাষা (i18n)

- কোডের স্থির লেখা আগের মতো চলবে: `t()` আর `src/i18n/en.ts`।
- ডাটাবেস থেকে আসা লেখা দেখানো হবে **শুধু `pick(bn, en)`** দিয়ে। এর মধ্যে আছে প্রকল্পের নাম ও বর্ণনা, ফিল্ডের লেবেল, স্ট্যাটের লেবেল আর একক শব্দ। ফাংশনটি `src/i18n/core.ts`-এ যোগ হবে। নিয়ম: ইংরেজি মোডে `en` খালি না থাকলে `en`, নইলে বাংলা।
- `i18n-check`-এ যোগ হবে:
  - কেউ `t(x.name_bn)` বা `t(x.label…)` লিখলে সতর্কবার্তা।
  - অব্যবহৃত প্রকল্প-শিরোনামের key (`en.ts:100-116`) মুছে ফেলা।
  - অকেজো `stripAliasArrays` সরানো।
- নতুন স্ক্রিপ্ট `npm run content-check`: কোথায় ইংরেজি খালি তা দেখায়। শুধু সতর্কবার্তা দেয়, ব্যর্থ হয় না।
- "ঘর" শব্দ ঢালাওভাবে বদলানো যাবে না, কারণ `en.ts:289, 443-444`-এ এর মানে শীটের ঘর (cell)। প্রকল্পভেদে যে লেখা বদলায়, তা টেমপ্লেট হবে, যেমন `'{n} টি {unit}'`।
- টাকা দেখানো:
  - বাংলায় `৳ ১,২৩,৪৫৬`।
  - ইংরেজিতে প্রশ্ন ৯-এর উত্তর অনুযায়ী।
  - হেল্পার থাকবে `src/lib/money.ts`-এ।

### ৫.১৪ ফ্রন্টএন্ডের কাঠামো

```
src/backend/            ← features/housing/backend সরে আসবে (interfaces, supabase, rest, factory) — সব প্রকল্পের জন্য
src/features/projects/  পাবলিক পেইজ, প্রকল্প রেজিস্ট্রি (registry/), ফিল্ড-টাইপ রেজিস্ট্রি (fields/), কম্পোনেন্ট
src/features/admin/     এডমিন পেইজ, প্রকল্প/ফিল্ড/স্ট্যাট বিল্ডার, শেয়ার্ড UI (Step, Badge, Field, inputClass)
src/features/geo/       bdGeo, geo.ts, geoMatch.ts, ইউনিয়ন লোডার, ম্যাপ
src/lib/money.ts        টাকার ফরম্যাট ও পার্স
src/lib/fuzzyMatch.ts   looseKey, nearDuplicates (ক্যাটাগরির কাছাকাছি বানান ও ভূগোল দুই জায়গাতেই)
```

**Adapter নিয়ম বহাল থাকবে:** UI কখনো সরাসরি Supabase ডাকবে না।
- নতুন ইন্টারফেস `ProjectsApi` (`getProjectsApi()`)। এর Supabase adapter থাকবে, আর REST adapter আপাতত stub।
- বিদ্যমান `HousingApi`-এর নাম বদলাবে না, শুধু নতুন ক্ষমতা যোগ হবে:
  - `union_name` ও `extra`।
  - ক্যাটাগরি ফিল্টার `.contains('extra', {key: value})`। key সংজ্ঞার সাথে মিলিয়ে whitelist হবে, মান sanitize হবে।
  - `getPrivate()` ও `setPrivate()`।
  - `stats(key)` চলবে `project_stats` দিয়ে।
- টাইপ:
  - `ProjectType` union-এর বদলে `ProjectKey = string`; পুরনো নামটি alias হিসেবে থাকবে।
  - নতুন টাইপ: `Project`, `ProjectField`, `FieldType`, `PhotoMode`, `GeoDepth`, `StatCardDef`, `ProjectStats`, `ProjectOverview`।
  - `erasableSyntaxOnly`-এর কারণে enum নয়; `as const` আর string union ব্যবহার হবে।

**পুরনো ডাটাবেসেও চলা (SQL চালানোর আগে বা পথ খ-তে):**
- adapter প্রথমবার কোনো নতুন জিনিস না পেলে তা মনে রাখে, আর সেই সেশনে পুরনো পথে চলে। "না পাওয়া" চেনা হয় এই কোড দিয়ে:
  - টেবিল নেই: `PGRST205` বা `42P01`
  - ফাংশন নেই: `PGRST202` বা `42883`
  - কলাম নেই: `PGRST204` বা `42703`
- **রেজিস্ট্রি:** `projects` টেবিল না থাকলে আসে `fallbackProjects.ts`-এ রাখা ঘর নির্মাণের ৩টি সারি।
- **স্ট্যাট:** `project_stats` না থাকলে `housing_stats` ডাকা হয় (`housing` হলে `null`, `semi_pucca` বা `tin` হলে নিজের key)। ফলাফল নতুন শেপে রূপান্তর হয়: `fields:{}`, `by_union:{}`, `distinct.unions:0`। বছরের তালিকা আসে `by_year` থেকে।
- **ওভারভিউ:** `projects_overview` না থাকলে প্রতিটি উপ-প্রকল্পে একটি করে `housing_stats` কল। শুধু এই অবস্থায় হোম পেইজে ৩টি পর্যন্ত কল অনুমোদিত।
- **লেখা:** `union_name` আর `extra` payload-এ যায় শুধু তখন, যখন প্রকল্পটি এগুলো ব্যবহার করে, অর্থাৎ `geo_depth='union'` অথবা কোনো কাস্টম ফিল্ড আছে। ঘর নির্মাণে এগুলো কখনো পাঠানো হয় না, তাই পুরনো ডাটাবেসে লেখাও ঠিকমতো চলে।
- **পরীক্ষা:** dev-এ `VITE_SIMULATE_LEGACY_DB=1` দিলে adapter এমন আচরণ করে যেন নতুন জিনিসগুলো নেই। `npm run smoke -- --legacy` এই মোডে পুরো সাইট পরীক্ষা করে। এটি গোপন কিছু নয়, তাই `.env.example`-এ মন্তব্য হিসেবে থাকবে।

**প্রকল্প রেজিস্ট্রি** (`src/features/projects/registry/projectsStore.ts`):
- মডিউল-স্তরের promise cache, যা `useSyncExternalStore` দিয়ে পড়া হয়। ভাষা টগলের সময় `LanguageProvider`-এর remount একে ছোঁয় না।
- `localStorage` স্ন্যাপশট `asf_projects_v1` (try/catch সহ) থেকে প্রথম পেইজ সাথে সাথে আঁকা হয়; পেছনে নেটওয়ার্ক থেকে মিলিয়ে নেওয়া হয়। স্ন্যাপশট কখনো লেখার কাজে ব্যবহার হয় না।
- এডমিন সেশনে খসড়াসহ লোড হয়। এডমিন প্যানেল সবসময় তাজা ডাটা আনে, আর সেভের পর store invalidate করে।
- হুক ও হেল্পার: `useProjects()`, `useProject(key)`, `projectPath(project)`, `childrenOf(group)`।

**রাউটিং:**
- `App.tsx`-এ স্থির রাউট: `/`, `/admin/login`, `/admin/*`, আর `/housing/admin/*` (`LegacyAdminRedirect`)।
- রেজিস্ট্রি থেকে তৈরি রাউট:
  - গ্রুপ: index-এ `GroupLandingPage`, তারপর তার উপ-প্রকল্পগুলো।
  - একক প্রকল্প: `ProjectListPage`, যার child রাউট `:serial` (lazy `ProjectDetailPage`)। **Outlet-মডাল প্যাটার্ন অপরিবর্তিত।**
- `*` রাউট যায় `ConfigAwareNotFound`-এ। এটি 404 দেখায় **শুধু নেটওয়ার্ক থেকে রেজিস্ট্রি মিলিয়ে নেওয়া শেষ (বা ব্যর্থ) হওয়ার পর**, শুধু স্ন্যাপশট দেখে কখনো নয়। তাই সদ্য প্রকাশিত প্রকল্পের ডিপ লিংকেও ক্ষণিকের 404 দেখা যায় না।
- খসড়া প্রকল্পের রাউট খোলে শুধু লগইন করা এডমিনের জন্য, সাথে হলুদ ব্যানার "খসড়া — শুধু এডমিন দেখছেন"।

**ফিল্ড-টাইপ রেজিস্ট্রি** (`src/features/projects/fields/fieldTypes.ts`):
- প্রতিটি ধরনের জন্য `parse(raw, def)`, `format(value, def, lang)`, `toCsv(value, def)`, `Input` আর `Cell`।
- `resolveFields(project)` সিস্টেম আর কাস্টম ফিল্ড মিলিয়ে একটি তালিকা দেয়।
- ফর্ম, ইম্পোর্ট, CSV, টেবিল, বিস্তারিত আর লগ সবাই এই **একটি উৎস** ব্যবহার করে। এর সার্ভার-সাইড প্রতিরূপ §৫.৭-এর ট্রিগার।

**হেডার:**
- হোম, একটি "প্রকল্পসমূহ ▾" ড্রপডাউন, আর ভাষা টগল। ড্রপডাউনের কারণ: লম্বা বাংলা নাম 768px-এ উপচে না পড়ে।

- ফোন ও ট্যাবে টেবিলের বদলে কার্ড।

## ৬. বিদ্যমান ঘর নির্মাণ প্রকল্পের মাইগ্রেশন

### ৬.১ নীতি: Expand → Migrate → Contract

1. **Expand (M-ধাপ ২–৩):** ডাটাবেসে শুধু নতুন জিনিস যোগ হবে। পুরনো সাইট (তখনকার কোড) হুবহু চলবে।
   - `semi_pucca` আর `tin` প্রকাশিত অবস্থায় seed হবে।
   - `housing_stats` আর `housing_years` wrapper হিসেবে থাকবে।
   - পুরনো কোড `extra` পাঠায় না, তাই কিছু ভাঙে না।
2. **Migrate (M-ধাপ ৪–১৫):** UI ধাপে ধাপে নতুন কাঠামোয় যাবে। প্রতিটি ধাপের পর ঘর নির্মাণ দেখতে ও কাজে আগের মতো থাকবে, আর নতুন SQL চালানো না থাকলেও চলবে (§৫.১৪)।
3. **Contract (অনেক পরে, ঐচ্ছিক):** wrapper আর পুরনো কোড সরানো হবে, তবে শুধু তখন যখন grep, `security-check` আর `smoke` নিশ্চিত করবে যে এগুলো আর কেউ ব্যবহার করছে না।

### ৬.৩ ফিঙ্গারপ্রিন্টের সঠিক সংজ্ঞা

শুধু **পুরনো কলামগুলো** ধরা হয়। `updated_at` আর নতুন কলাম (`union_name`, `extra`) বাদ, তাই সফল মাইগ্রেশনের পরে ভুল করে "মেলেনি" আসবে না। সময়গুলো UTC-তে নেওয়া হয়, যাতে সেশনভেদে ফলাফল না বদলায়।
```sql
select project_type,
       count(*)       as records,
       max(serial_no) as max_serial,
       md5(string_agg(row(
         id, project_type, serial_no, year, name, father_or_husband_name,
         division, district, upazila, address,
         prev_photo_url, prev_thumb_url, current_photo_url, current_thumb_url,
         prev_photo_source, current_photo_source,
         photo_updated_at at time zone 'UTC', created_at at time zone 'UTC'
       )::text, E'\n' order by serial_no)) as fingerprint
from public.housing_beneficiaries
group by project_type order by project_type;
```
সাথে আরও যা নেওয়া হয়:
- `housing_serial_counters` (`project_type`, `last_serial`)।
- লগের `count(*)` ও `max(id)`।
- `housing_stats(null)`-এর JSON।
- একটি **স্কিমা-ফিঙ্গারপ্রিন্ট**: `public` স্কিমার টেবিল/কলাম/ধরন, constraint-এর নাম, পলিসির নাম, আর ফাংশনের নাম ও আর্গুমেন্ট, সাজানো তালিকার md5। rollback rehearsal এটা ব্যবহার করে।

তিন জায়গায় ব্যবহার:
1. **`checks/00_baseline.sql` (M-ধাপ ১):** এই মানগুলো দেখায়। আপনি ফলাফল AI-কে পাঠাবেন।
2. **প্রতিটি মাইগ্রেশন ফাইলের ভেতরে:** শুরুতে মানগুলো একটি অস্থায়ী টেবিলে রাখা হয়, শেষে আবার হিসাব করে মেলানো হয়। একটিও না মিললে ফাইলটি নিজেই ত্রুটি দেয়: "ফিঙ্গারপ্রিন্ট মেলেনি — কিছুই বদলায়নি"। পুরো ট্রানজেকশন বাতিল হয়।
3. **`checks/10_verify.sql`:** AI M-ধাপ ১-এর বেসলাইন মান ফাইলে বসিয়ে দেবে। ফলাফলে প্রতিটি চেকের পাশে একটি করে লাইন আসবে: **"মিলেছে ✅"** বা **"মেলেনি ❌"**। M-ধাপ ১ আর SQL চালানোর মাঝে আপনি পুরনো প্যানেলে নতুন রেকর্ড যোগ করে থাকলে, AI আগে বেসলাইন আবার চালাতে বলবে।

### ৬.৫ ব্যাকআপ (প্রতিটি মাইগ্রেশন ফাইলের আগে)

2. তৈরি করা ব্যাকআপ ফাইলটি চালান (§১.৩-এর নিয়মে)। এটি একটি `backup` স্কিমায় কপি রাখে, যা API-তে খোলা নয়। প্রতিটি ধাপের নাম আলাদা, তাই একই দিনে দুবার চালালেও "already exists" ত্রুটি আসে না।

| ফাইল | কখন | কী কপি করে |
|---|---|---|
| `backup/before_10.sql` | SQL ১০-এর আগে (১০b-ও এতে ঢাকা) | `beneficiaries_m2`, `serial_counters_m2`, `activity_log_m2`, `serial_changes_m2` |
| `backup/before_11.sql` | SQL ১১-এর আগে | উপরের সবগুলো `_m3_11` নামে, সাথে `projects`, `project_fields`, `beneficiary_private` |
| `backup/before_12.sql` | SQL ১২-এর আগে | একই, `_m3_12` নামে |

ফাইলের ধরন (উদাহরণ):
```sql
create schema if not exists backup;
revoke all on schema backup from anon, authenticated;
create table if not exists backup.beneficiaries_m2 as table public.housing_beneficiaries;
create table if not exists backup.serial_counters_m2 as table public.housing_serial_counters;
-- … বাকিগুলো একইভাবে
```
`public` স্কিমায় ব্যাকআপ রাখলে anon তা পড়তে পারত। Supabase-এর ফ্রি প্ল্যানে point-in-time recovery নেই, তাই **এই কপিগুলোই একমাত্র রোলব্যাক।**

### ৬.৬ রোলব্যাক ও তার মহড়া

`rollback/10_12_rollback.sql` অংশে অংশে লেখা: ১২, তারপর ১১, তারপর ১০b, তারপর ১০। প্রতিটি অংশ `if exists` দিয়ে লেখা, তাই শুধু ১০ চালানো থাকলেও, অথবা সবগুলো চালানো থাকলেও, একই ফাইল কাজ করে। যা করে:
- `09_activity_log.sql`-এর `housing_log_record_change` ফেরত আনে, যাতে লগ-ফাংশন মুছে-ফেলা কলাম খুঁজে না পায়।
- `housing_stats`, `housing_years`, `housing_next_serial` আর `housing_bulk_update_by_serial`-এর পুরনো সংস্করণ ফেরত আনে।
- নতুন ট্রিগার ও ফাংশন সরায়।
- পুরনো public-read পলিসি আর পুরনো CHECK ফেরত আনে, FK সরায়।
- নতুন কলাম আর টেবিল সরায়।

সতর্কতা:
- এটি **নিরাপদ শুধু ততক্ষণ, যতক্ষণ নতুন প্রকল্পে কোনো রেকর্ড নেই।** নতুন প্রকল্পে ডাটা আসার পর পথ হলো ব্যাকআপ থেকে পুনরুদ্ধার।
- **মহড়া** (`checks/rollback_rehearsal.sql`): `begin;` → রোলব্যাকের পুরো বডি → স্কিমা-ফিঙ্গারপ্রিন্ট, ডাটা-ফিঙ্গারপ্রিন্ট আর `housing_stats(null)` বেসলাইনের সাথে মেলানো → `rollback;`। তাই মহড়ায় আসলে কিছুই বদলায় না। SQL Editor একটি ফাইল থেকে আরেকটি ফাইল টেনে আনতে পারে না, তাই একটি ছোট স্ক্রিপ্ট রোলব্যাক ফাইল থেকে মহড়া ফাইলটি তৈরি করবে। এতে দুটোর বডি সবসময় হুবহু এক থাকে।
- কোড ফেরত নেওয়া যাবে git দিয়ে। এর জন্য প্রতিটি ধাপের শেষে লোকাল কমিট দরকার (প্রশ্ন ১৮)।

### ৬.৭ বিপজ্জনক পুরনো ফাইল

`08_reset_test_data.sql` সব রেকর্ড মুছে কাউন্টার শূন্য করে দেয়। এখন লাইভ ডাটা আছে, তাই এটি আর `06_seed.sql` সরানো হবে `supabase/sql/dev/`-এ। সাথে গার্ড বসবে: রেকর্ড আছে এবং `set asf.confirm_reset = 'YES'` দেওয়া হয়নি, তাহলে ফাইলটি থেমে যাবে।

### ৬.৮ পরীক্ষা প্রকল্প

নতুন ফর্ম, ইম্পোর্ট আর ছবির পরীক্ষা হবে একটি খসড়া **"পরীক্ষা প্রকল্প"**-এ (key, slug ও প্রিফিক্স সবই `demo`), কখনো লাইভ ঘর নির্মাণে নয়। এটি তৈরি হবে M-ধাপ ৭-এ, প্যানেলের উইজার্ড দিয়ে। এর আগের ধাপগুলোতে লেখার পরীক্ষা শুধু SQL selftest-এ হবে, একটি অস্থায়ী key (`zz_selftest`) দিয়ে, ROLLBACK-এর ভেতরে।

শেষে দুটি পথ:
- রেকর্ড মুছে প্রকল্পটি `dev/remove_demo_project.sql` দিয়ে সরানো। এটি সেশন-ফ্ল্যাগ `asf.allow_project_delete='on'` আর DEFINER ফাংশন ব্যবহার করে।
- অথবা প্রকল্পটি চিরকাল অপ্রকাশিত রেখে দেওয়া।

### ৬.৯ ডাটাবেস কখন চালাবেন: দুই পথ (প্রশ্ন ১৪)

আগে আপনি ঠিক করেছিলেন: **ডাটাবেসের কাজ সব ধাপ শেষে একসাথে** (`docs/HOUSING_PROGRESS.md`-এর উপরে লেখা আছে)। সেই নিয়ম তখন ঠিক ছিল। এখন দুটি জিনিস বদলেছে: লাইভ ডাটা আছে, আর এডমিন প্যানেল আসল টেবিল ছাড়া পরীক্ষা করা যায় না। তাই এই পরিকল্পনায় সুপারিশ আগের নিয়ম থেকে আলাদা। আপনি যেকোনো পথ বেছে নিতে পারেন:

|---|---|---|
| কখন চালাবেন | M-ধাপ ২ ও ৩-এর শেষে (সারি ২৫–৩০) | M-ধাপ ১৬-এর শুরুতে, সব একসাথে |

| ঝুঁকি | কম; প্রতিটি ধাপে ভুল সাথে সাথে ধরা পড়ে | অনেক কোড পরীক্ষা ছাড়াই জমে থাকে; শেষে অনেক ভুল একসাথে বেরোতে পারে |

**গেট মানে পরীক্ষার গেট, কোড লেখার গেট নয়।** কোনো ধাপের কোড লেখা ডাটাবেসের জন্য আটকে থাকবে না। ডাটাবেসের সব করণীয় আগের মতোই যাবে `docs/HOUSING_PROGRESS.md`-এর চেকলিস্টে।

## ১১. প্রতিটি ধাপের সাধারণ নিয়ম

1. **এক বার্তায় একটি ধাপ।** উত্তর বাংলায়। কোনো অনুমান করলে স্পষ্ট করে লেখা হবে, চুপচাপ কখনো নয়। ডিফল্ট প্রয়োগ হলে §১২-এ লেখা হবে।
2. **শুরুতে পড়া:** পরিকল্পনা (M-১-এ ডেস্কটপের `ASF_MULTI_PROJECT_PLAN.md`, পরে `docs/MULTI_PROJECT_PLAN.md`) আর `docs/HOUSING_PROGRESS.md`।
3. **শেষে তিনটি অংশ:** (১) বদলানো ফাইল, (২) "আমাকে যা করতে হবে" (ডাটাবেসের কাজ শুধু চেকলিস্টের সারি নম্বর দিয়ে), (৩) কীভাবে পরীক্ষা করবেন।
4. **নথি আপডেট:** `docs/HOUSING_PROGRESS.md` সবসময়। REST চুক্তি বদলালে `docs/API_CONTRACT.md`, সংস্করণসহ। SQL যোগ হলে `supabase/README.md`-এর ক্রম।
5. **আগের কিছু ভাঙবে না।** প্রতিটি ধাপের পর সাইট চালু থাকবে, নতুন SQL চালানো থাকুক বা না থাকুক। ঘর নির্মাণ দেখতে আর কাজে আগের মতোই থাকবে।
6. **ভাষা:**
   - UI-এর সব লেখা বাংলায়, `t()` আর `en.ts` দিয়ে ইংরেজি টগল।
   - ডাটাবেসের লেখা শুধু `pick()` দিয়ে।
   - সংখ্যা `formatBanglaNumber`/`toBanglaNumber` দিয়ে, টাকা `formatTaka` দিয়ে।
7. **গোপন key:**
   - service_role, সার্ভারের পাসওয়ার্ড বা টোকেন কখনো ফ্রন্টএন্ড কোডে বা git-এ যাবে না।
   - service_role থাকবে শুধু রুটের `.env`-এ, স্ক্রিপ্টের জন্য, কখনো `VITE_` প্রিফিক্সে নয়।
   - `.env.local` gitignored থাকবে।
8. **adapter নিয়ম:** UI কখনো সরাসরি Supabase ডাকবে না। সব যাবে `HousingApi`, `ProjectsApi`, `AuthProvider` আর `ImageStorage` দিয়ে, যেগুলো `VITE_HOUSING_BACKEND` বেছে নেয়।
9. **নিরাপত্তা সার্ভারে:**
   - লেখার অধিকার শুধু এডমিনের, প্রয়োগ হবে RLS আর ট্রিগার দিয়ে।
